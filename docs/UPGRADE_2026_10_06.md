## 数据范围

公开 OpenFootball 数据按同一个上游提交下载，并保存提交 SHA、原始字节 SHA-256、抓取时间和原文地址。脚本兼容上游 `score.ft` 对象和简写比分数组，未开赛的无比分记录不填成 0:0。

2026-10-06 导入时：2021-22 至 2025-26 每季 380 场赛果；2026-27 380 场赛程，其中 50 场有赛果。后者是下载时的快照，不是实时比分。

积分由档案赛果计算，不含扣分等行政处罚。因此例如 2023-24 的计算积分不等于包含扣分后的官方积分；页面已说明。跨赛季比较提供场均积分，进行中的赛季不可直接与完整赛季总积分比较。原有 2024-25 球员统计不与最新实时名单合并。

数据源与接口参考：
- OpenFootball：https://github.com/openfootball/football.json （CC0-1.0）
- API-Football：https://www.api-football.com/documentation-v3
- BBC Sport RSS：https://feeds.bbci.co.uk/sport/football/rss.xml
- 球员照片：https://resources.premierleague.com ，照片权益和历史统计许可相互独立。

API_FOOTBALL_KEY 仅放后端。实时缓存为单进程共享：比分默认 60 秒、每日赛程 5 分钟、首发 10 分钟、新闻 15 分钟、现役名单 6 小时、转会 24 小时、伤病 4 小时。实际新鲜度还取决于上游覆盖与更新频率。共享缓存合并同时订阅，失败后延迟重试。默认 Compose 使用一个后端 worker；多副本部署需另配共享缓存与共享限流，不能直接照搬单进程配置。免费或低额度套餐可能无法持续承受比分轮询，间隔可通过 LIVE_POLL_SECONDS 调大。

## 在现有 Windows 项目中运行

先备份现有项目。新压缩包是完整源码，解压到新文件夹更容易回退；若覆盖原目录，覆盖源码时保留你自己的 `.env`，数据库先备份。

在 VS Code 项目根目录打开两个终端。现有虚拟环境与依赖可继续使用，不需要重新建环境。

终端一（后端）：

```powershell
cd backend
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

后端启动会自动执行新的 Alembic 迁移，保留原数据并新增账户表。

终端二（前端）：

```powershell
cd frontend
npm ci
npm run dev -- --hostname 0.0.0.0
```

使用 Node >=22.13。电脑浏览器打开 http://localhost:3000 。访问 `/history`、`/live`、`/account`。生产构建验证可执行 `npm run lint`、`npm run build`；后端验证为 `python -m pytest`。

如果已有 `frontend/.env.local`，把 `NEXT_PUBLIC_API_BASE_URL` 改为空，新增或保留：

```dotenv
NEXT_PUBLIC_API_BASE_URL=
API_INTERNAL_URL=http://127.0.0.1:8000
```

修改后重启前端。这样浏览器请求同域 `/api`，Next 代理到后端；无需修改所有页面。

实时数据在 `backend/.env` 配置：

```dotenv
API_FOOTBALL_KEY=你自己的数据源Key
LIVE_POLL_SECONDS=60
```

配置后重启后端。不要使用 `NEXT_PUBLIC_API_FOOTBALL_KEY`，不要提交实际 Key。

手机和电脑连接同一个局域网，手机打开 `http://电脑局域网IP:3000`；允许防火墙访问 3000。若手机要注册登录，将这个准确地址加入 `backend/.env` 的 FRONTEND_ORIGINS，例如：

```dotenv
FRONTEND_ORIGINS=http://localhost:3000,http://127.0.0.1:3000,http://192.168.1.10:3000
```

重启后端。手机浏览器不会再尝试连接自己的 localhost:8000。开发模式 Cookie 可用于 HTTP；正式上线只用 HTTPS。

更新公开历史档案，在项目根目录执行：

```powershell
python scripts/sync_history.py
```

脚本支持 `--seasons 2023-24 2024-25` 和 `--commit 完整上游SHA`。下载失败不覆盖对应赛季的旧文件；每季写入采用临时文件原子替换。更新后的历史 JSON 需要一同提交才能带到部署环境。

## 部署到有域名的服务器

需要一台安装 Docker Compose 的服务器、域名 DNS 指向该服务器，并开放 80/443 端口。当前交付提供部署配置，不含云服务器或公网地址。没有 Docker 运行环境的本次验证未执行容器构建/启动。

1. 将项目完整上传服务器，根目录复制 `.env.example` 为 `.env`。
2. 将 `PUBLIC_HOST` 替换为你的真实域名（不带 https:// 或路径）；填入可选 API_FOOTBALL_KEY；原有 AI 功能需要时追加 DASHSCOPE_API_KEY。
3. 执行：

```bash
docker compose up -d --build
docker compose ps
docker compose logs --tail 100 backend frontend caddy
```

4. 打开 `https://你的域名`，检查 `/api/health`、登录刷新、赛季档案和比分推送。Caddy 自动申请 HTTPS 证书。

SQLite 和登录会话在 `database` 命名卷中。更新代码可以重新 build；不要执行 `docker compose down -v`，这会删除数据库。备份须包含数据库卷；公开发布前使用新数据库，或明确选择迁移本地数据库，不能把本地账户库直接提交 GitHub。

## GitHub 上传前检查

- 首页桌面四卡并排；手机左右滑动只影响卡片区域，页面不能整体横向溢出。
- 球员列表、详情、对比能辨认同一球员；断网或图片 404 时使用占位图；切换球员不残留上一人的错误状态。
- 切换历史赛季和球队，跨赛季行数、场次、积分、场均积分与赛果一致；当前赛季明确显示未完成范围。
- 注册 → 刷新仍登录 → 退出 → 再登录；错误密码被拒绝。已有数据库升级后原数据仍在。
- `/live` 无 Key 时显示“尚未接入”；有 Key 后验证真实赛程、球队 ID、首发/伤病/转会权限，空记录不等于没有伤病。
- 开启/暂停比分推送，不出现多重订阅；接口失败时显示旧数据时间或明确不可用。
- 预测概率之和为 100%，同队对阵和不足样本被拒绝；页面保留未校准说明。
- `npm run lint`、`npm run build`、`python -m pytest` 通过。
- 上传所有新增源文件、迁移与六份历史 JSON；不上传 `.env`、`.env.local`、数据库、node_modules、.next、虚拟环境、任何真实 Key。
- `git diff --check`、`git status` 确认改动范围，最后再上传。新包不含 `.git`，需覆盖你已有的 Git 工作目录，或按原来的 GitHub 网页流程逐个上传目录中的源码；GitHub 仓库不能直接把 zip 当成可运行源码。
